- 기획: 한지혜 (HD건설기계 원가기획)
- 개발일: 2026-08-26
- 저장소: https://github.com/aebonlee/hd-project12

## 1. 요구사항 분석 — 시안이 이미 있었다

이 기획서는 **화면 시안과 함께** 왔다. "과제 기획한 내용을 간단히 바이브 코딩해
보았습니다"라는 문장과 대시보드 한 장. 사이드바 구성, KPI 카드 4장, 도넛,
월별 추이, 오늘의 일정, 프로세스 5단계, 빠른 작업까지 이미 그려져 있었다.

그래서 이 작업의 몫은 화면을 새로 상상하는 것이 아니었다.
**시안이 정하지 않은 것을 찾아 채우는 것**이었다.

시안이 답하지 않은 질문들:

- '요청'에서 바로 '완료'로 바꿀 수 있는가?
- 산출물 파일이 없는데 "제출됨"으로 둘 수 있는가?
- 요청자가 올린 수정본은 수행자의 초안을 덮는가?
- 외부 수행자에게 남의 품번이 보이는가?
- 승인을 거둔 계정에 배정돼 있던 건은 어떻게 되는가?

기획서 본문을 다시 읽으니 답이 있었다. 이 다섯은 전부 **지금 공유 엑셀에서
실제로 어긋나고 있는 자리**였다. 기획자가 "관리가 어렵습니다"라고 쓴 것이 그 뜻이다.

**그래서 이 프로젝트의 목표를 "시안을 웹으로 옮기는 것"이 아니라
"공유 엑셀이 막지 못하던 것을 규칙으로 못 박는 것"으로 잡았다.**

## 2. 규칙을 두 곳에 적기로 한 이유

처음에는 `js/logic.js` 하나로 충분해 보였다. 화면이 막으면 되니까.

그런데 서버 모드(Supabase)를 붙이는 순간 이 전제가 깨진다.
브라우저는 그냥 REST 를 부르는 클라이언트일 뿐이고, anon 키는 공개 키다.
누구든 `curl` 로 `PATCH /rest/v1/request?id=eq.REQ-001` 을 보내면
`status: '완료'` 가 그대로 들어간다. 화면의 판정은 지나가지도 않는다.

그래서 **같은 규칙을 `supabase/schema.sql` 에 다시 적었다.**

| 규칙 | 브라우저 | 서버 |
|---|---|---|
| 상태 한 칸씩 | `Logic.canTransition` | `enforce_status_flow` 트리거 |
| 산출물 0건이면 제출 불가 | 같음 | 같음 |
| 되돌릴 때 사유 필수 | 같음 | 같음 |
| 초안/수정본 버전 분리 | `Logic.nextVersion` | `unique (request_id, kind, version)` |
| 희망완료일 ≥ 요청일 | `Logic.validateRequest` | `check (due_date >= requested_at)` |
| 수행자는 자기 건만 | `Logic.visibleRequests` | `request_read` RLS |

두 곳에 같은 규칙을 적으면 **어긋날 위험**이 생긴다. 그 위험을 테스트로 덮었다.
`scripts/sqltest/run.sh` 가 임시 PostgreSQL 을 띄워 스키마를 실제로 적용하고,
브라우저 테스트와 **같은 문장**으로 서버 쪽을 확인한다.

실제로 이 방식이 한 번 잡아 준 것이 있다.
`Logic.isApproved()` 를 처음에는 "수행자만 승인 상태를 본다"로 썼는데
(`user.role !== WORKER || status === '승인'`), 서버의 `my_role()` 은 역할과 무관하게
승인된 계정에만 역할을 돌려준다. 즉 **승인 전 요청자는 데모에서는 다 보이고
서버에서는 아무것도 안 보이는** 상태였다. 서버 쪽을 기준으로 브라우저를 고쳤다.

## 3. 파일명 해독 — 기획서가 물은 것

> AI가 파일명만 보고 찾아서 알아서 넣을 수 있는지..
> (EX. 부품원가계산서_20150103 으로 저장되어 있기 때문에 일자별로 찾기도 가능할 것 같음)

이 문장이 이 프로젝트에서 가장 재미있는 요구였다.

먼저 확인한 것: **모델을 부를 필요가 없다.** 파일명은 짧고 패턴이 정해져 있다.
필요한 건 정규식과 순서다. 오히려 어려운 쪽은 "읽는 것"이 아니라
**"못 읽었을 때 지어내지 않는 것"** 이었다.

만들면서 걸린 자리들:

**① 품번을 먼저 떼어 내지 않으면 날짜가 틀린다.**
`PCT_123456-100001_240115.xlsx` 에서 날짜부터 찾으면 `123456` 이 잡힌다.
품번(6+6자리)을 먼저 제거하고 남은 문자열에서 날짜를 찾도록 순서를 바꿨다.

**② 품번이 6+5 인 줄 알았다.**
시안의 `123456-100001` 을 6자리-5자리로 읽고 정규식을 `\d{6}-\d{5}` 로 썼다.
테스트에서 품번이 하나도 안 잡혀 세어 보니 `100001` 은 여섯 자리였다.
`\d{6}-\d{6}` 으로 고쳤고, 이 값이 그대로 DB `check` 제약이 되었다.

**③ `20250230` 을 날짜로 받으면 안 된다.**
2월 30일은 없다. 정규식만으로는 걸러지지 않아서 윤년까지 보는 `validYmd()` 를 따로
두고, 통과 못 하면 **버리고 사유를 남긴다** — "8자리 숫자가 있으나 달력에 없는
날짜입니다". 그냥 null 로 두면 왜 비었는지 아무도 모른다.

**④ `201501` 의 일자를 1일로 채우고 싶은 유혹.**
그러면 표가 예뻐진다. 하지만 없던 정보가 생긴다. 1월 3일 자료를 1월 1일로
검색하게 된다. 그래서 `docDate` 는 비우고 `docMonth` 만 채운 뒤,
**일자 구간 검색에서는 아예 제외**한다. 조용히 섞이면 "찾았다"고 착각한다.

**⑤ 확신도를 사람에게 넘기기.**
품번+일자가 다 읽히면 `high`(자동 확정), 하나만이면 `medium`, 아무것도 없으면 `low`.
`high` 만 자동 확정하고 나머지는 [보정] 단추를 남긴다.
샘플 46건 중 23건이 확인 대상으로 남는데, 이게 정직한 숫자다.

이 규칙을 DB 제약으로도 옮겼다 —
`check (not confirmed or part_no is not null or doc_date is not null or doc_month is not null)`.
아무것도 못 읽은 자료를 '확인됨'으로 표시하면 검색에서 영영 못 찾는다.

## 4. 용량과 권한 — 기획서가 막막해한 두 문장

> 약간의 용량 문제와 사내 팀즈 연동 시 권한 문제 등이 예상될 것 같은데
> 어떻게 해결해야할 지가 약간 막막한 부분이긴 합니다.

이 두 문장은 "나중에 생각할 것"이 아니라 **설계를 가르는 요구사항**이었다.

**용량.** 부품원가계산서 한 건이 수 MB, 품번마다 초안 여러 판 + 수정본.
파일을 시스템이 들고 있으면 브라우저든 무료 DB 든 몇 달 안에 막힌다.
그래서 **파일 본문을 저장하지 않기로** 정하고, 그 결정을 코드 세 곳에 못 박았다.

- `js/store.js` 첫머리 주석 — 왜 담지 않는지
- `deliverable` 표에 파일 본문 칼럼이 아예 없다. `link` 만 있다
- 화면에도 적는다 — "업로드한 파일은 이름·크기만 기록되고 본문은 어디에도 저장되지 않습니다"

이 시스템은 저장소가 아니라 **색인**이다. "이 품번의 최신본이 어디의 몇 번째 판인가"
를 아는 것이 원래의 문제였고, 파일을 옮기는 것은 그 문제가 아니었다.

**권한.** Teams/SharePoint 연동은 사내 승인이 필요하고 언제 날지 모른다.
연동을 전제로 만들면 승인 날 때까지 아무것도 못 쓴다.
그래서 **연동 없이 오늘 쓸 수 있게** 만들고, 붙는 지점을 `link` 한 칸으로 좁혔다.
메일도 같은 이유다 — 서버가 직접 보내지 않고 `mailto:` 로 클라이언트를 연다.
사내 메일 서버 권한이 없어도 오늘 쓸 수 있고, 보내는 것은 사람이 확인한 뒤다.

## 5. 만들면서 고친 것

**샘플 데이터의 날짜를 고정하지 않았다.**
`requestedAt: '2026-08-20'` 처럼 박아 두면 세 달 뒤 이 데모를 열었을 때
164건이 전부 '지연'으로 빨갛게 된다. 시드에는 **오늘로부터의 일수**(`requestedOff: -12`)
만 담고, `store.js` 가 불러올 때 실제 날짜로 만든다.

**시드에 정답을 적지 않았다.**
보관 자료 46건의 품번·일자를 시드에 미리 적어 두면 편하지만,
그러면 해독기가 망가져도 화면은 멀쩡해 보인다. 시드에는 **파일명만** 담고
불러올 때 `Logic.parseArchiveName()` 으로 그 자리에서 읽는다.

**퍼센트 합이 100이 되게 맞췄다.**
도넛 옆 숫자를 그냥 반올림하면 39+22+11+28 이 99나 101이 된다.
보고 화면에서 이건 눈에 띈다. 최대잉여법으로 나머지를 배분해 합을 100에 고정하고
테스트로 묶었다(3등분 33.33% 같은 경우 포함).

**표 한 행이 두 배 높이가 되던 것.**
공통 테마(`css/hd-theme.css`)에는 안내 띠용 `.warn { margin: 22px 0 }` 규칙이 있다.
상태 배지에 `class="badge warn"` 을 붙였더니 그 규칙까지 걸려
'검토/수정'·'임박' 행만 89px 로 부풀었다. 테마가 함께 제공하는 별칭
`badge-warn` 으로 바꿔 색과 ■ 표식은 그대로 두고 여백만 피했다.
공용 파일을 고치지 않고 쓰는 쪽에서 해결한 것이다.

**164행을 한 번에 뿌리지 않는다.**
작업 요청 목록이 164행이면 스크롤 말고는 아무것도 못 한다.
50행씩 끊고 "전체 164건 중 50건을 보고 있습니다" 를 함께 적는다.
잘라 낸 사실을 숨기면 "다 봤다"고 착각한다. 조건을 바꾸면 다시 50행부터 센다.

**열이 많은 표는 접지 않고 굴린다.**
11열짜리 표를 폭 100% 에 욱여넣으면 셀 안에서 줄이 접혀 표가 문단처럼 보인다.
내용만큼 넓히고(`width:auto; min-width:100%`) 넘치면 감싼 상자를 가로로 굴린다.

| 파일 | 무엇을 보는가 | 개수 |
|---|---|---|
| `test/logic.test.js` | 상태 전이 · 입력 검증 · 버전 · 일정 · 집계 · 권한 · 메일 · 파일명 해독 | 114 |
| `test/store.test.js` | 요청 → 수행 → 제출 → 검토 → 완료 한 바퀴, 부수 효과 | 72 |
| `test/server.test.js` | 어댑터가 Store 와 같은 모양인지, 서버 거절 시 되돌리는지 | 40 |
| `test/smoke.browser.js` | 브라우저에 실제로 띄워 일곱 화면·권한 경계·표 높이·반응형 | 25 |
| `scripts/sqltest/20_project.local.sql` | 같은 규칙을 진짜 PostgreSQL 이 막는지 | 26 |

화면 연기 테스트를 따로 둔 이유가 있다. 규칙 테스트가 전부 통과해도 `app.js` 의
오타 하나면 페이지가 빈 화면이 된다 — 규칙은 맞는데 아무도 그것을 볼 수 없는 상태다.
실제로 표 한 행이 두 배 높이가 되던 문제(§5)는 어떤 단위 테스트도 잡을 수 없었고,
브라우저에서 높이를 재고서야 원인이 공통 테마의 `.warn` 여백이라는 것을 알았다.
그래서 그 측정을 테스트로 굳혔다 — `#reqTable` 의 모든 행이 60px 이하일 것.

playwright 가 없으면 이 테스트는 **조용히 건너뛴다.** 이것 하나 때문에
`node test/*.test.js` 가 막히면 아무도 안 돌리게 되기 때문이다. CI 에서는 설치하고 돌린다.

`test/fake-supabase.js` 는 PostgREST 흉내만 내지 않고 **schema.sql 의 트리거와
같은 규칙**을 건다. 그래야 "브라우저는 통과시켰는데 서버가 막는" 자리를 테스트가 잡는다.

서버 어댑터의 쓰기는 낙관적이다 — 규칙 판정을 먼저 돌려 통과한 것만 메모리에
반영하고 서버로 보낸다. 서버가 거절하면(RLS·트리거) **조용히 넘기지 않고 알린 뒤
서버 상태로 다시 읽어 온다.** 화면이 서버보다 앞서 나간 채로 남는 것이 가장 나쁘다.
이 동작도 테스트로 고정했다(`fake._deny('request:update', ...)`).

## 7. CI 와 브랜치 보호

`main` 을 보호하려면 요구할 상태 체크가 하나는 있어야 한다. 그래서
`.github/workflows/test.yml` 을 만들어 PR 마다 위 다섯 가지를 전부 돌린다.

만들면서 하나 고쳤다. `scripts/sqltest/run.sh` 가 PostgreSQL 을 찾을 때
macOS 홈브루 경로와 `PATH` 만 뒤지고 있었다. 데비안·우분투(그리고 GitHub 러너)에서는
`initdb` 가 `PATH` 에 없고 `/usr/lib/postgresql/<버전>/bin` 에 있어서,
러너에 PostgreSQL 이 깔려 있는데도 "찾지 못했습니다"로 끝났다.
리눅스 경로를 뒤지는 단계를 넣고 안내 문구에도 `apt-get` 줄을 더했다.

브랜치 보호 자체(force push 금지 · 삭제 금지 · 필수 상태 체크)는 저장소
Settings 에서 켜는 것이라 코드로 들어오지 않는다. README 「개발 / 테스트」에
어디를 눌러야 하는지 적어 두었다.

## 8. 남은 것 / 실적용 시 손댈 곳

- **Teams/SharePoint 연동** — 지금은 `link` 칸에 URL 을 손으로 붙인다.
  Graph API 로 폴더를 훑어 자동으로 채우는 것이 다음 단계다. 붙는 지점은 그 한 칸이다.
- **메일 자동 발송** — 지금은 `mailto:`. 사내 SMTP 나 Graph 권한이 열리면
  Supabase Edge Function 한 개로 바꿀 수 있다. 발송 이력 표는 이미 있다.
- **첨부 실물 보관** — Supabase Storage 로 옮기려면 `link` 에 Storage 경로를 넣으면 된다.
  표 구조는 바뀌지 않는다. 용량 정책만 먼저 정하면 된다.
- **품번 마스터 연동** — 지금은 품번을 손으로 넣는다. 사내 마스터가 붙으면
  품명·모델을 자동으로 채울 수 있다.
